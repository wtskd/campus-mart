# 校园易站 CampusMart — 项目方案设计

> 课程：企业实习（1012-1230）　提交形式：个人提交　项目类型：前后台多端微服务项目
> 文档版本：v1.0　日期：2026-10-27

---

## 1. 项目概述

**一句话定位**：面向高校的二手闲置交易平台，后台管理（Web）+ 用户端（小程序/H5）+ 数据分析大屏 + AI 智能能力，采用 Spring Cloud Alibaba 微服务架构。

**为什么选这个题目**：它天然覆盖课程四条硬性要求，且业务数据天然适合做统计分析——

| 课程要求 | 本项目落点 | 可交付的"证据" |
|---|---|---|
| ① 后台管理：权限、动态菜单、日志、基础数据 | 基于 RBAC 的管理后台：用户/角色/菜单/学院/字典/公告/轮播/操作日志/登录日志 | 不同角色登录看到不同菜单；日志表有真实记录 |
| ② 前台用户端（小程序/uniapp/APP） | uniapp(Vue3) 一套代码 → 微信小程序 + H5 | 手机端完整走通「浏览→收藏→下单→完成→评价」 |
| ③ 数据分析统计模块 | 预聚合统计 + ECharts 图表 + 数据大屏 | GMV 趋势、分类占比、转化漏斗、RFM 分层 |
| ④ AI 模型调用 | LLM 一键发布、智能客服(RAG)、个性化推荐、内容审核 | 后台"AI 调用日志"页可看到每次调用的模型/耗时/token |

**加分说明**：项目内所有 AI 调用（模型、耗时、token、成败）落库并可在后台查询，答辩时是"真的调了模型"的硬证据；若已有技术类高级证书/竞赛获奖，按规定可直接评优秀，报告中需单独列一节说明。

## 2. 总体架构

```
┌─────────────────────────────── 客户端层 ───────────────────────────────┐
│  微信小程序 / H5 (uniapp)          Web 管理后台 (Vue3+ElementPlus)      │
│                                          数据大屏 (Vue3+ECharts)       │
└───────────────────────────────┬────────────────────────────────────────┘
                                │ HTTPS / JSON
┌───────────────────────────────▼────────────────────────────────────────┐
│  Nginx（静态资源 + 反向代理）                                            │
│  Spring Cloud Gateway :8081（路由 / JWT 校验 / 白名单 / 限流）            │
└───────────────────────────────┬────────────────────────────────────────┘
                                │ Nacos 服务发现 + OpenFeign
┌──────────┬──────────┬─────────┴───┬────────────┬────────────┬───────────┐
│ auth     │ system   │ item        │ analysis   │ ai         │ (可选)chat│
│ :9200    │ :9201    │ :9202       │ :9203      │ :9204      │ :9205     │
│ 登录认证 │ 权限菜单 │ 商品订单    │ 统计聚合   │ LLM/推荐   │ WebSocket │
│ 发Token  │ 日志字典 │ 收藏评价举报│ 大屏/报表  │ 审核       │ 站内聊天  │
└──────────┴──────────┴─────────────┴────────────┴────────────┴───────────┘
                                │
┌───────────────────────────────▼────────────────────────────────────────┐
│ 支撑层：MySQL 8（业务库 campus_mart）  Redis（缓存/验证码/限流）         │
│         Nacos 2.3.2（注册+配置）  本地文件存储（可替换 MinIO）           │
└────────────────────────────────────────────────────────────────────────┘
                                │
┌───────────────────────────────▼────────────────────────────────────────┐
│ AI 层：LLM Provider（远程 OpenAI 兼容接口 / 本地 Ollama，配置切换）      │
│        推荐引擎（ItemCF 离线计算）  内容审核（敏感词 DFA + LLM 复核）     │
└────────────────────────────────────────────────────────────────────────┘
```

**服务间调用关系**：`item` 调 `ai`（发布时生成文案、详情页推荐）；`analysis` 读 `item`/`system` 数据做聚合（本期简化为同库读表 + Feign 取数）；`gateway` 统一鉴权后把 `userId`/`userType` 放入请求头下传，下游服务不再重复解析 Token。

## 5. 数据库设计（详见 `sql/01-schema.sql`）

按域分前缀，共 29 张表（已在 MySQL 8.0.44 上执行验证通过）：

| 域 | 表 | 说明 |
|---|---|---|
| 系统域 `sys_` | `sys_user` `sys_role` `sys_menu` `sys_user_role` `sys_role_menu` `sys_dept` `sys_dict_type` `sys_dict_data` `sys_config` `sys_oper_log` `sys_login_log` `sys_file` | RBAC + 动态菜单 + 日志 + 基础数据 |
| 业务域 `biz_` | `biz_category` `biz_item` `biz_order` `biz_favorite` `biz_comment` `biz_report` `biz_message` `biz_notice` `biz_banner` | 二手交易主流程 |
| 统计域 `stat_` | `stat_overview_daily` `stat_category_daily` `stat_funnel_daily` `stat_user_rfm` | 预聚合结果表，管理端只查这些表 |
| AI 域 `ai_` | `ai_prompt_template` `ai_call_log` `ai_knowledge` `ai_recommend` | Prompt 可运营 + 调用可观测 + RAG 知识库 + 推荐结果 |

**核心设计决策**：

1. **商品状态机**：`0草稿 → 1待审核 → 2在售 → 3已预订 → 4已售出`，另有 `5已下架 / 6违规`。状态流转集中在 `item` 服务的 `ItemStatusMachine`，避免散落在各处 if。
2. **订单与商品一对一**：二手交易天然是单品，`biz_order.item_id` 唯一约束，不做购物车（省 1 周工作量且不影响演示）。
3. **统计不扫明细**：管理端所有图表只读 `stat_*` 表，由 `@Scheduled` 每小时增量聚合，答辩可讲"读写分离思想"。
4. **AI 调用全链路可观测**：所有 LLM 调用经 `AiGateway` 统一出口，必写 `ai_call_log`（含 token 与耗时），失败也记。
5. **中文全文检索**：`ai_knowledge.content` 建 `FULLTEXT ... WITH PARSER ngram`，用 MySQL 原生能力做 RAG 召回，免去向量库部署负担（这是本项目最讨巧的一处设计）。

## 6. 接口规范

统一响应体：

```json
{ "code": 200, "msg": "操作成功", "data": {...}, "traceId": "..." }
```

- 业务错误码：`200` 成功 / `401` 未登录 / `403` 无权限 / `500` 服务异常 / `600x` 业务异常
- 分页参数：`pageNum`、`pageSize`，返回 `{ total, rows }`
- 鉴权：`Authorization: Bearer <JWT>`，网关校验后向下游注入 `X-User-Id`、`X-User-Type`（`admin` / `app`）
- 幂等：下单接口用 `biz_order.order_no` 唯一索引 + Redis `SETNX` 双重保证
- 完整接口清单在 `docs/03-api.md`（脚手架完成后由代码生成，保持与实现一致）

## 7. AI 方案（要求 ④ 的核心）

### 7.1 能力矩阵

| 场景 | 类别 | 实现 | 演示效果 |
|---|---|---|---|
| **AI 一键发布** | LLM 文案生成 | 输入 3~5 个关键词/成色/价格 → 输出标题+描述+建议定价+标签 | ⭐⭐⭐⭐⭐ 现场最直观 |
| **智能客服** | LLM + RAG | 平台规则/交易流程知识库 → 检索 top3 → 拼 Prompt 回答 | ⭐⭐⭐⭐ |
| **个性化推荐** | 推荐算法 | ItemCF 离线算 + 热榜/同校/同类兜底，混合排序 | ⭐⭐⭐⭐ |
| **内容审核** | LLM + 规则 | 敏感词 DFA 初筛 → LLM 二次判定是否违规 | ⭐⭐⭐ |
| （选做）**图片识别分类** | CV | 多模态模型识别商品类别自动选类目 | ⭐⭐⭐ 时间够再做 |

> 说明：课程只要求"AI 模型调用"一类即可，本项目做了 LLM + 推荐两类，且预留 CV 扩展点，属于超额完成。

### 7.2 模型接入设计（本地/远程可切换）

远程与本地统一走 **OpenAI 兼容协议**，因此同一份客户端代码即可切换：

```yaml
ai:
  provider: remote          # remote | local
  providers:
    remote:
      base-url: https://api.deepseek.com/v1
      api-key: ${AI_API_KEY}
      model: deepseek-chat
      timeout: 30s
    local:
      base-url: http://localhost:11434/v1    # Ollama 的 OpenAI 兼容端点
      api-key: ollama
      model: qwen2.5:7b-instruct
      timeout: 60s
```

```java
public interface AiProvider {
    AiResult chat(AiRequest request);          // 统一出口
    boolean support(String model);
}
```

- 远程推荐：DeepSeek-V3 / 通义 qwen-plus / 智谱 GLM-4-Flash（有免费额度，成本最低）
- 本地：Ollama + `qwen2.5:7b-instruct-q4_K_M`，本机 RTX 4060 8G 显存可跑
- 答辩话术："模型层做了 provider 抽象，业务代码不感知具体模型，换模型只改配置"

### 7.3 稳定性设计（防演示翻车）

1. **超时+重试**：连接 3s / 读 30s，失败重试 1 次
2. **降级兜底**：超时或限流 → 返回模板化文案（商品文案有 5 套模板），页面上提示"AI 生成中，已为你填充模板"
3. **熔断限流**：Sentinel 对 `/ai/**` 做 QPS 限流（如 5 QPS），单用户 20 次/分钟
4. **成本控制**：Prompt 长度截断、结果 Redis 缓存 24h、`ai_call_log` 统计日消耗
5. **可观测**：后台"AI 调用监控"页可按场景/模型/日期查看成功率、平均耗时、token 消耗——**这一页本身就是数据分析模块的一部分，一箭双雕**

### 7.4 Prompt 管理

`ai_prompt_template` 表存模板，后台可在线编辑、启用停用、调整 temperature/max_tokens，改完即时生效（Redis 缓存 key 失效）。这是"AI 能力运营化"的加分点。

## 8. 数据分析模块（要求 ③ 的核心）

### 8.1 指标体系

| 主题 | 指标 | 口径 |
|---|---|---|
| 交易大盘 | GMV、订单数、成交率、客单价 | GMV=已完成订单金额之和（不含取消） |
| 增长 | 新增用户、日活 DAU、次留/7 留 | 新增=当日首次登录；活跃=当日有任一行为 |
| 商品 | 发布量、在售量、售出率、平均成交周期 | 售出率=已售出/累计发布 |
| 分类 | 各分类成交额/订单量占比、Top10 | 关联 `biz_category` |
| 漏斗 | 浏览→收藏→下单→完成 转化率 | 基于行为明细日聚合 |
| 用户价值 | RFM 分层（重要价值/重要保持/一般发展/流失预警） | R=最近交易距今天数，F=交易次数，M=交易金额，五分位打分 |
| AI 运营 | 调用次数、成功率、平均耗时、token 消耗 | 来自 `ai_call_log` |

### 8.2 技术实现

- **聚合任务**：`AnalysisJob` 每小时跑增量，每日 01:00 跑 T-1 全量重算；用 `@Scheduled` + 分布式锁（Redis）防重复
- **查询**：管理端只查 `stat_*`，单表 + 时间索引，毫秒级
- **展示**：ECharts（折线/柱状/饼图/漏斗/仪表盘）+ 独立**数据大屏**路由（深色主题、数字翻牌、自动轮播）
- **导出**：EasyExcel 导出订单/商品/统计报表（管理端用）

### 8.3 大屏内容

顶部数字翻牌（今日 GMV / 订单 / 新增用户 / 在售商品）→ 30 日交易趋势折线 → 分类成交占比环形 → 转化漏斗 → 学院/校区热力分布（用柱状图模拟，避免地图组件依赖）→ AI 调用实时滚动。

## 9. 非功能设计与安全

| 项 | 措施 |
|---|---|
| 认证 | JWT 双端隔离（`admin` / `app`），Token 2h 过期 + Redis 黑名单支持登出 |
| 授权 | 接口级 `@RequiresPerm("item:audit")` + 角色-菜单-按钮三级；数据权限按学院（答辩可提） |
| 越权 | 所有"我的XX"接口强制用 Token 里的 userId，禁止前端传 userId |
| 注入 | MyBatis-Plus 参数绑定；排序字段白名单 |
| 上传 | 类型/大小白名单、随机文件名、图片二次压缩、存储路径不可执行 |
| 限流 | 网关 + Sentinel，登录/短信/AI 接口单独限流 |
| 日志 | 操作日志 AOP（谁/什么时间/调了什么/参数/结果/耗时/IP）+ 全链路 traceId |
| 幂等 | 下单防重（唯一索引 + Redis 锁）、重复提交拦截 |

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Nacos 版本旧（1.4.0）不兼容 Boot3 客户端 | 服务注册失败 | 下载 Nacos 2.3.2；失败则降级用 Nacos 1.4 + SCA 2021 分支（备选方案已演练） |
| 微信小程序需 https 备案域名 | 真机无法请求 | 演示用 H5 + 开发者工具"不校验合法域名"；答辩讲清生产化差异 |
| AI API 额度/网络波动 | 演示卡死 | 模板兜底 + 本地 Ollama 备用 + 提前录屏 |
| Docker 不可用 | 一键部署失败 | 用 `start-all.bat` 多进程启动脚本 + 详细部署文档 |
| 9 周单人开发 | 功能做不完 | 砍掉购物车、真实支付、实时聊天；主线优先 |
| 代码全部由 AI 生成，答辩被问懵 | 影响成绩 | 每个模块都要能讲出"为什么这么设计"，文档里保留设计决策记录 |

## 13. 答辩预设问题（提前准备）

1. 为什么用微服务？单体也能做，你的拆分依据是什么？→ 按业务边界拆，认证与业务分离便于横向扩展；同时说明"这个体量用单体也合理，选微服务是为了满足课程要求并练习治理能力"（诚实回答反而加分）
2. 网关做了哪些事？Token 怎么校验？下游怎么拿到用户信息？
3. 动态菜单怎么实现的？权限到按钮级怎么控制？
4. Nacos 的作用？服务挂了会怎样？（注册中心 + 心跳 + 负载均衡）
5. 统计为什么不直接查明细表？预聚合怎么保证数据准确？
6. AI 调用的成本怎么控制？模型挂了怎么办？
7. 推荐算法用的什么？冷启动怎么解决？（热榜 + 同类 + 随机兜底）
8. 遇到过最难的 bug 是什么？怎么定位的？（准备 2~3 个真实案例）
